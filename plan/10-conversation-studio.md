# M2：对话式小说工作台与 OpenAI 接入

日期：2026-09-10。状态：接口与工作流已实现；无真实凭据，尚未进行付费调用及模型写作质量评估。

## 产品判断

用户需要的是能一起构思、读稿和修改的创作搭档。对话承担意图表达，正文承担创作成果，作者通过稿件审阅掌握决定权。两者不能混成一个不断增长的聊天记录。

典型过程：打开本章 → 引用一段 → “让他明明想念却装作不在意，不增加往事” → AI 返回建议与改稿 → 对照原文 → 保存或定稿。讨论不自动触发成文，修改只创建提案。

与通用聊天的差异来自可操作的作品状态：章纲与原作边界自动携带；选择的稿件有确定版本；改稿有原文与范围；采用会留下新修订。不能把“加几个角色提示词”当成差异化已成立。

## 视觉与信息层级

- 正文是主舞台，右侧创作搭档是持续可见的协作区；设定、执行和版本收进次级标签。
- 深炭灰导航与对话面板形成稳定框架，暖象牙色正文承载阅读，赭金只标识引用、操作和修改。
- 正文 18px、约 2 倍行距、每行避免过长；工具 11–13px，重要正文与工具文本保持对比。
- 缩短作品标题区，明确区分应用边框、工作台、纸面。避免浅色卡片堆叠、低对比细字和大面积无意义留白。
- 桌面输入框固定在对话面板底部，长对话独立滚动；窄屏正文与对话上下排布，引用动作将焦点送至对话输入框。
- 设计提案 `/concept/` 演示行内删改、采用、保留原文和专注模式，始终标明示例，不写数据库。正式应用目前是展开修改前全文、编辑修改后全文，尚无完整逐字 diff。

## 已实现的服务闭环

浏览器 POST conversation → PostgreSQL 保存请求/基准版本 → worker 领取 → 组装有限上下文 → OpenAI Responses API → 讨论文本 SSE / 结构化稿件 → Draft → 作者采用 → Revision。

- `GET /api/v1/ai/status`：只返回配置状态、模型和参数，不回传密钥。
- `POST /api/v1/branches/{bid}/conversation`：discuss / write / revise。绑定 scene、draft 或 plan，可携带唯一选中文字。基于已保存正文，拒绝过期或外部路线目标。
- `GET /api/v1/branches/{bid}/conversation`：恢复本路线最近 40 个对话任务和关联稿件。界面标明旧版本历史；模型仅复用同版本、同目标最近 8 条消息。
- 沿用 jobs 的查询、停止、SSE、trace 及 drafts 的编辑/定稿。讨论没有草稿；稿件不会在生成时写入正史。
- revise 生成整章或仅生成选段替换文字；后者由服务端在冻结原文中替换唯一匹配，其他文字原样保留。重复选段要求重选，避免替错。
- 原稿与改稿对照信息从 job 请求和 Draft 读取；作者定稿后才替换末章。较早章节仍要求分支，保留后文。

模型输入包含：作者指令、作品 brief、开场、人物公开设定、公开事实、匹配章纲、最近三章、当前稿件、选中文字与有限近期对话。没有自动导入原作，没有向量召回，也不声称知道整部长篇。

这是作者助手，不是角色扮演代理。未公开角色知识在代码中排除。下一阶段引入角色视角时，必须先建立焦点人物和已发生观察事件，不能把所有角色秘密塞进每个角色上下文。

## 配置与调用约束

本机 `backend/.env` 已准备空配置。填写真实值后重启 API 和 worker：

```dotenv
MODEL_PROVIDER=openai
OPENAI_API_KEY=填入本机密钥
OPENAI_MODEL=填入账户可调用且支持所需能力的模型ID
AI_MAX_OUTPUT_TOKENS=4096
AI_TIMEOUT_SECONDS=120
```

支持模型名配置，不擅自替换不支持的模型。讨论要求文本 Responses；起稿/改稿还要求 Structured Outputs。当前端点固定官方 OpenAI，不声称支持所有“兼容 OpenAI”的代理服务。

- `.env` 已被忽略；加载时系统环境变量优先。密钥不放前端、不进入提示词、状态 API 或日志。
- 不提供无需正文的“连接测试”来暗中产生费用。实际发送是计费请求，正文和上下文会传给 OpenAI。
- 单任务一次模型调用；输出上限默认 4096 tokens，可设 256–12000；总输入序列化上限 60000 字符。后者不是精确 token 计数，供应商仍可能拒绝过长输入。
- 使用 `store=false`，不依赖供应商会话作为正史；这不等于对供应商全部数据保留政策作零保留承诺。
- 每 2 秒续租，30 秒租约，最长任务默认 120 秒；网络调用不持有数据库事务。
- SDK 自动重试关闭。调用前保存 ModelCall；进程崩溃或结果不明时不自动二次收费，标记 CALL_OUTCOME_UNKNOWN。
- 取消阻止晚到结果落成草稿，但不能保证供应商撤销已发生的计算与计费。记录能取得的 usage；无法取得标明未知，金额返回 null，不能显示零费用。
- 稿件 JSON 严格结构验证不等于人物一致性或文笔质量验证。输出截断、格式错误、拒绝、超时均不生成正式稿件。

## 如何逐步让 AI 写好小说

当前先做一位可控的作者搭档，每次解决一个场景或修改要求。不要在尚未验证单次成文效果前增加多角色调用成本。

1. 构思阶段让作者明确场景目标、人物欲望、阻力、发生的变化和结束位置。讨论模式用来补齐这些信息，不自动向作品档案写入设定。
2. 成文阶段遵守视角、原作锚点、不可改边界和作者文风偏好。生成正文与简短修改说明分开。
3. 审稿阶段先校验引用和版本，再由作者核对人物、原作与新增事实。当前没有额外模型语义审校。
4. 后续增加“事实变更提案”：识别谁在何时知道了什么、人物关系如何变化、伏笔新增/回收；作者确认后建立投影，供下一章使用。
5. 长篇再引入逐章摘要与带来源的召回，保留时间线和未解决伏笔。必须能解释引用来源；不能用无来源摘要替换锁定事实。

质量验证计划：用自建原创与虚构同人材料构成固定场景集，比较不同模型的可采用率、作者修改字数、人物知情越界、视角切换、情绪解释重复、响应时间和 token 用量。没有真实调用前不宣布哪个模型中文最佳，不宣称商业价值已验证。
