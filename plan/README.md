# 故事工坊产品与实施计划

日期：2026-09-10。状态：已开始搭建，M0 本地流程原型已实现；真实模型尚未接入。最新进展见 `08-implementation-status.md`。

## 产品边界

构建面向小说、原创角色和同人创作的文字故事工坊。核心体验是：阅读章节后，探索角色私密档案和同一事件的另一视角，并能从关键事件建立新的故事分支。首版不做 AI 生图。

后端必须维护人物记忆、信息边界、因果关系和版本，减少用户反复提醒模型的成本。多 Agent 是实现手段，不作为质量更高的先验结论；与同模型单次提示方案进行对照验证。

## 已采用的默认决策

- Python 3.12、FastAPI、Pydantic 2、SQLAlchemy 2、Alembic、PostgreSQL；具体版本在 P0 核验兼容性并锁定。
- 单仓库、模块化单体；API 与 worker 分进程，使用同一业务代码。
- 首版使用 PostgreSQL 中的持久化任务表和有界状态机。暂不引入 Redis、Celery、LangGraph、向量库或微服务。
- 多角色共享模型接入能力，但上下文独立。首个真实模型供应商在集成阶段选择，不写死模型名称。
- 正文、番外及事实变更先成为草稿，经用户接受后才能进入故事正史。
- 私密档案和另一视角首版只补充表达，不能静默新增决定性历史事实。
- 分支点首版限定为场景边界；场景内部修改从该场景开始重写。首版不合并分支。
- 初始容量：一个世界 2～5 名主要角色，一次生成一个场景，角色提案每次最多调用 3 个角色。
- 用户触发任务可以在离开页面后继续。定时自动连载和自动接受草稿放到后续阶段。

## 仍需通过实践确定

- 哪个模型在中文叙事、结构化输出和指令遵循之间最合适。
- 单个场景长度、延迟和成本目标的实际可达性。
- 用户更愿意使用哪种私密档案，以及是否为连续创作付费。
- 生产部署地区、账号服务与供应商数据处理配置。

这些问题不阻塞本地骨架和 mock 工作流开发；真实模型调用需要供应商配置和可用凭据，上线需要完成部署与数据处理决策。
