# 前端产品与体验设计

日期：2026-09-10。状态：已据此搭建部分原生网页并连接本地后端，覆盖阅读、草稿、档案与分支。完整设计仍有待办，详见 `08-implementation-status.md`。下述心理预期是待验证假设。

## 1. 核心产品承诺

暂定体验名称「未尽」，仅为概念名，未做商标/域名可用性检查。

主文案：**故事之外，还有他们没说出口的话。**

补充文案：写下你的人物，读他们的故事，探索另一面，也为他们选择另一种可能。

用户应把产品理解为一个持续保存自己作品的创作空间。避免将角色塑造成现实中正在等待用户回应的人，不用内疚或催促制造回访。

## 2. 心理期待与对应体验

| 心理期待（假设） | 设计响应 | 禁止的反效果 |
| --- | --- | --- |
| 我的人物被理解 | 创建时锁定 1～3 个重要特点；生成后可纠正并影响后续 | 先填几十项设定，或不断跑偏 |
| 我想了解他的另一面 | 章节后出现有依据的私密档案/另一视角 | 为反转临时改写人物历史 |
| 我想保留自己的解释 | 不看番外也能继续；允许不接受某个草稿 | 强行揭开所有内心，消灭留白 |
| 我能影响故事 | 在关键场景建立另一条路线 | 选择很多但后续内容没有实质区别 |
| 修改不会毁掉作品 | 分支前明确原稿保留，一键切回 | 直接覆盖，用户不敢试 |
| 我写的东西属于我 | 显示保存状态、可导出、可删除 | 默认公开、强迫分享或扣住作品 |
| 我不用反复下指令 | 入口绑定当前人物和场景，少量目标即可继续 | 每次从空白聊天框解释背景 |

## 3. 优先人群和验证边界

首批面向已有原创人物或人物关系构想、愿意参与修改的写作者。暂不同时满足纯追更读者、专业长篇工作室、聊天陪伴和互动游戏用户。

主要价值时刻：读到角色的一段隐藏表达后，对刚才的正文产生新的理解；随后能保留原稿，尝试自己的情节选择。不是功能点击量，也不是生成字数。

## 4. 首次进入

首页仅给两条入口：「体验一段故事」「写我的人物」。

### 示例体验

- 使用自建原创、已审阅、预先存储的短场景，不等待实时生成，不冒充正在运行的 AI。
- 标记「示例故事」，展示正文 → 未寄出的信 → 原文回看 → 另一种可能。
- 目标是两分钟左右完成一次理解，不要求登录后才能知道产品是什么；是否允许游客保存另行实现。
- 示例事件必须提前固定，私密内容与正史一致。不得根据点击随机制造秘密。

### 创建自己的故事

第一步：两个人是谁、他们是什么关系、一句话开场。支持用户自由输入；类型选项只提供起步建议，不覆盖用户内容。

第二步：系统整理为简短人物卡，用户选择锁定项。首版每个人展示名字、一句话特点、想要什么、一个可选秘密。补充世界设定收起。

第三步：确认生成范围「先写一个场景」，说明消耗上限、可离开页面、结果为待确认稿。前端只显示后端提供的额度信息。

不展示 Agent 数量、温度、图编排或 token 配置；这些放在开发设置，不是普通创作路径。

## 5. 信息架构

一级：我的故事 → 故事阅读/创作页。账号和偏好位于低强调位置。

故事内：阅读为默认；人物与设定、章节与路线使用按需打开的侧栏/抽屉。避免常驻三列工作台挤压正文。

返回首页时展示最近阅读段落、当前路线和真实待确认稿。不默认用统计仪表盘、连续签到和推荐广场占据首页。

## 6. 主阅读页

桌面：窄顶栏 + 居中正文（约 38～42 个汉字的行宽）+ 章末探索区。正文是最大视觉区域，作者工具按需出现。

顶栏：返回故事架、故事名、当前路线、人物与设定入口。当前路线不能隐藏，避免用户以为自己覆盖了原稿。

正文：章节、场景标题、小型视角标记、段落。只为真正可分支的场景放轻量动作；不把每句话装饰成按钮。

章末探索区最多展示 2 个相关入口：

- 「一封未寄出的信 · 林舟」
- 「同一晚 · 许岚的视角」

独立次级操作「如果当时……」，主要操作「继续下一幕」。当尚无合格档案时不摆放伪造锁卡；作者可主动「写一份私密档案」。

发现不是抽卡：没有倒计时、稀有度、未读红点轰炸和强制付费悬念。

## 7. 私密档案交互

已接受且满足阅读条件：点击直接阅读，不请求模型，不重复收费。桌面正文旁临时展开文书区域；窄屏在正文后展开，提供「收起，回到原文」。

内容包含文书类型、所属角色、场景锚点。表现为简洁信纸排版，不用图片拟物造成加载或可读性成本。

尚未生成：作者点击「创作这封信」，明确这是新草稿和实际额度。生成后先显示「待确认」，按钮为「收进故事」「修改」「暂不采用」。采用需要执行 accept；阅读揭示执行 reveal；前端不得把两个行为混同。

作者首次阅读草稿必然可能得知内容，不能承诺“作者审阅完但仍完全保留秘密”。剧透保护是显示偏好，不是从作者记忆中撤销信息。

关键信息不足：用具体问题请求确认，例如「这封信是否真的写于车站重逢之前？」不自动补出颠覆事件。

## 8. 多视角交互

标注「同一事件 · 另一视角」，区别于新剧情。切换后保留原文滚动位置；提供返回原视角。

首版采用单栏切换；不要强制双栏全文逐句比较。用户若只想保留正文的暧昧和留白，可以完全跳过。

当前视角中的信息可能是信念、误解或自述；界面不用“真相”标签把它当作全知事实。

## 9. 改变剧情与分支

入口在场景末或作者选中文本菜单。弹出一个简短面板：

> 从「车站告别」开始，写另一种可能。
> 原来的故事会保留。
> 你想改变什么？[她在列车启动前回头。]

显示实际重写起点：场景内部选句也从场景起点分支，与后端规则一致。新路线先出现待确认稿；不会立即改为默认路线。

生成后显示原路线和新路线的名字、改动起点及简短摘要；摘要只引用已生成内容。生成前不预告未知结局。

用户可以「保留这条路线」「继续原来的故事」。路线选择器按最近使用列出，首版不做复杂无限树图和分支合并。

分支创建成功但后续生成失败：保留空分支和改动指令，可重试或删除空分支；不伪装成从未创建。

## 10. 作者工作状态

阅读和编辑使用明确模式切换。编辑模式展示锁定设定、正文编辑、保存状态和提交差异。阅读时不常驻问题列表。

- 本地未保存：明确提醒离开风险。
- 草稿已保存：显示已保存，不显示已纳入故事。
- 待确认稿：显示接受后的影响，主要按钮「收进故事」。
- 版本冲突：保留用户稿件，提供「以此另开路线」「返回查看新版本」，不自动覆盖。
- 设定冲突：定位问题段落，用自然语言解释，例如「许岚还不知道信被截走，这一句提前透露了她尚未获得的信息」。

锁定设定的显式修改必须展示所改内容。普通接受稿件无需重复确认弹窗；只有有实际损失或大范围影响才增加确认。

## 11. 等待和异常

| 状态 | 用户看到什么 | 可用操作 |
| --- | --- | --- |
| 排队 | 正在等待开始 | 离开、取消 |
| 生成 | 正在写这一幕；真实阶段 | 离开、取消 |
| 检查 | 正在核对人物与前文 | 离开、取消 |
| 成功 | 新稿已准备好 | 阅读、接受、修改 |
| 需确认 | 一条具体问题 | 补充后再生成 |
| 失败 | 已保留内容及失败原因摘要 | 重试、返回 |
| 预算到达 | 本次已停止；显示可用用量信息 | 阅读已有稿件、以后再试 |
| 连接中断 | 正在恢复连接 | 查看任务状态 |

不得使用虚假百分比和“角色正在思考你”式文案。演示中的预制结果明确标记。reader 不接收未经审核的流式正文；作者预览标注未审核。

## 12. 视觉方向

关键词：文学、私密、留白、可编辑。以字号、行距、段落和文书结构形成质感；无需人物头像或封面生图。

- 浅色阅读面采用暖纸色与深墨色，强调色少量用于选中与行动；提供深色主题。
- 中文正文优先本机宋体/衬线字体，界面控件使用系统无衬线字体，保留字体加载失败回退。
- 正文建议 18～20px、约 1.8～2 行高；设置允许调整，不把长篇排成密集管理界面。
- 微动效只服务展开、折叠和焦点变化，尊重减少动态效果偏好，不逐字慢放阻碍阅读。
- 320px 起无横向溢出；手机工具置于可点击菜单，信件和分支面板纵向展开。
- 正文颜色符合 WCAG AA 对比目标，触控操作区约 44px；键盘可完成所有主要动作。
- 已隐藏的秘密不能存在于 DOM、无障碍标签、标题 tooltip 或预加载响应中。概念示意可内置原创示例数据，必须声明其不是生产权限实现。

## 13. 与现有 API 对齐

| 前端行为 | 后端契约 |
| --- | --- |
| 继续下一幕 | POST branch/jobs；SSE；GET draft |
| 收进故事 | POST draft/accept，expected_revision |
| 看已接受的信 | POST artifact/reveal |
| 创作一封信 / 另一视角 | POST branch/jobs，对应 kind；不得自动循环生成 |
| 新路线 | POST branch/forks，随后在新分支创建 job |
| 人物锁定项 | setting-drafts → accept |
| 回到阅读位置 | reading-progress |

客户端缓存键必须带用户、world、branch、revision、mode、阅读进度/解锁状态；退出、切换身份、删除或撤回可见性时清理关联缓存。不可用前端隐藏代替服务端裁剪。

## 14. 原型范围与验收

本轮提供一份原创预置内容的交互示意，展示正文、未寄出的信、另一视角、两条路线切换。没有连接模型、没有真实保存和额度结算，不代表完整产品已实现。

下一轮前端实现顺序：阅读与章末探索 → 草稿接受 → 分支 → 人物设置 → 创建引导 → 故事架。先使用受契约约束的 mock 接口，再连接后端。

首轮找 5 名目标用户观察：

1. 无解释能否理解正文和私密档案的关系。
2. 是否认为另一视角与正文一致，是否带来值得阅读的新信息。
3. 能否分清草稿、已接受内容和已解锁内容。
4. 是否敢于分支，能否找回原稿。
5. 是否愿意用自己的角色再创作一次；哪些功能打断了阅读。

不把点击信件当作价值已验证；结合访谈、主动续写和修改负担。首轮优先修正概念误解和内容不一致，再打磨装饰。
